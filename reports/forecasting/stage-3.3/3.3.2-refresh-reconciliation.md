## 2. Контракт extraction run (реализовано)

Каждый запуск получает детерминированный идентификатор:

```
run_id = <interval>-<response_hash[0..12]>-<first_date>_<last_date>
```

Атрибуты контракта: `run_id, started_at, finished_at, shop_no, slice_id, metric, requested_from, requested_to, timezone, source_identifier, request_hash, response_hash, rows_received, rows_valid, rows_rejected, status, completeness, http_status, interval_label, run_dir, file_hashes[], validation[], notes[]`.

Фактические запуски (файловые манифесты в `data/extraction/superset/stage-3.3/runs/`):

## 6. Инцидент и его устранение (важно)

Первая попытка расширения выполнялась в chart-режиме (`--charts 20624`) и дала **41 VALUE_CHANGED из 41**: chart-режим строит тело из `query_context` чарта и **теряет фильтры** `feature_tt IN ('ДаркСтор')` и `delivery_type_group IN ('Курьеры','Такси')`, которые есть в HAR-теле 103 → выборка становится шире.

Действия: расхождение не перезаписано, прежние данные восстановлены из архива (`archive/canonical_daily_delivered_orders.stage-3.2.csv`, checksum содержимого совпал с `233a86fc…`), ошибочные каталоги сохранены как свидетельства (`_mismatch-chartmode-*`), выгрузка переделана в HAR-режиме (`--files 103`), после чего сверка дала `IDENTICAL=41, VALUE_CHANGED=0`. Правило записи canonical ужесточено: запись разрешена только при `IDENTICAL`/`MATCH_WITH_EXTENSIONS`, отсутствии дублей и пропусков.

## 7. Ограничения

- Контракты запусков хранятся в файловой системе, а не в SQLite: запись в БД на этом этапе не выполнялась. При переходе к регулярному обновлению потребуется решение — расширять схему (`source_set`/`run_id` в наблюдениях) или оставить файловый журнал.
- Изменение исторических значений источником (VALUE_CHANGED) обрабатывается как отдельное событие и требует решения человека; автоматическая перезапись запрещена.
- Проверка «повторное использование старого run_id» реализована по хешу ответа; при смене формата манифеста потребуется миграция контракта.
