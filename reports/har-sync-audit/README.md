# Аудит: пригодность `har.har` как основного метода синхронизации локальной копии

Дата анализа: 2026-11-22 (Europe/Moscow).
Объект: `har.har` (2 135 959 байт) в корне репозитория.
Метод: программный разбор HAR (`tools/har-*.ts`), сверка с локальными артефактами
`reports/phase-01-6-2/` и `analysis_package/`, сверка с кодом клиентов Superset в `src/`.
Режим: только чтение. Сетевые запросы к Superset не выполнялись. Ничего в Superset не менялось.

---

## 1. Итог одной строкой

**Фактический HAR подтверждает теорию репозитория по каталогу метаданных (объекты и фильтры
совпадают до идентификаторов), но опровергает её главный блокер: `POST /api/v1/chart/data`
в реальной сессии работает и возвращает данные (56×200, 1×202 + опрос по ключу).**
При этом сам файл `har.har` **непригоден для наполнения локальной копии**: в нём нет ни одного
тела ответа, нет cookie, нет `Authorization`, а `X-CSRFToken` пустой. Как основной метод
синхронизации он не работает — работать может только **воспроизведение** его запросов
с собственной аутентификацией.

### 2.1 Что в HAR всё-таки есть полезного

Единственный содержательный слой — **тела POST-запросов**. Это 57 полных payload-ов
`/api/v1/chart/data` и 1 payload `filter_state`. Каждый содержит:

- `datasource: {id, type}` — целевой датасет;
- `queries[]` — `columns`, `metrics`, `filters` (col/op/val), `time_range`, `granularity`,
  `row_limit`, `extras.where`, `post_processing`;
- `form_data` — 62 ключа, включая `viz_type`, `datasource: "<id>__table"`, `slice_id`,
  `native_filter_id`, `defaultValue`, `multiSelect`, `result_format`, `result_type`, `client_id`;
- адресные query-параметры `?form_data={"slice_id":N}&dashboard_id=977`.

Это готовые, проверенные браузером запросы: их можно воспроизвести один в один.

| Метод | Путь | Кол-во | Статусы | Комментарий |
|---|---|---:|---|---|

| GET | `/api/v1/dataset/{id}?q=(columns:!(...))` | 38 | 200 — 38 | детали датасетов с выбором полей |
| GET | `/api/v1/time_range/` | 3 | 200 | серверное время для `today`/`tomorrow` |
| POST | `/api/v1/dashboard/977/filter_state?tab_id=3` | 2 | **403 — 2** | нет CSRF |
| GET | `/api/v1/dashboard/services_lite` | 1 | 200 | дашборд по slug |
| GET | `/api/v1/dashboard/services_lite/charts` | 1 | 200 | чарты дашборда |
| GET | `/api/v1/dashboard/services_lite/datasets` | 1 | 200 | датасеты дашборда |

| GET | `/api/v1/release_notes/status/`, `/manage/dynamic-plugins/`, `/dashboard/favorite_status/`, `/superset/language_pack/ru/` | 4 | 200 | служебное |

### 2.3 Асинхронный поток chart/data (важно для реализации)

```
POST /api/v1/chart/data?form_data={"slice_id":20161}&dashboard_id=977   → 202 (188 Б)
GET  /api/v1/chart/data/qc-5c6c9257f1f62234c723ae9ca9051a32            → 200 (1 217 Б)
```

Ключ результата (`qc-…`) выдаётся в теле ответа 202 и затем читается отдельным GET.
Тот же ключ в реальной сессии переиспользуется для следующих запросов по тому же чарту.

### 2.4 Распределение запросов данных

- По датасетам: 39 различных датасетов; больше всего `3035 darkstore_time_click` (14 запросов),
  `5979 darkstore_time_date_update` (2), `2293`, `2679`, `2693` (по 2).
- По `viz_type`: `filter_select` — 42, `table` — 4, `echarts_area` — 4, `pivot_table_v2` — 4,
  `filter_timecolumn`/`filter_timegrain` — по 1.
- `result_type`: `full` — 56.
- `row_limit`: 1 (проверка свежести), 100, 2 000 (значения фильтров), 10 000 (серии).

То есть по факту это **не выгрузка строк**, а: (а) значения фильтров для 44 колонок,
(б) 4 агрегированных чарта по `3035`, (в) одна проверка `max(date_update)`.

## 3. Сверка с теорией репозитория

### 3.1 Что говорит репозиторий

| Источник | Утверждение |
|---|---|
| `analysis_package/ANALYST_BRIEF.md` | «SQL Lab и chart data API: **недоступны** (403/401)»; `ACTUAL_VALUES = 0` |
| `docs/phase-01-6-2/02_access_results.md` | `chart_data` = **FORBIDDEN**, проба P22 `POST /api/v1/chart/data` → **401** |
| `docs/phase-01-6-2/02_access_results.md` | `sql_lab` = FORBIDDEN (403), `databases` = NO_VISIBLE_DATABASES |
| `reports/phase-01-6-2/superset_access_matrix.json` | `"chart_data": "FORBIDDEN"`, `databases_visible_count: 0` |
| `docs/phase-01-8/12_open_decisions_and_gaps.md` | `GAP-020` (P0_BLOCKER): SQL Lab и chart_data недоступны |
| `Отчет_исследования_Этап_1.7_Superset.md` | 18 SELECT не выполнены; `ACTUAL_DATA = 0` |

### 3.2 Что показывает HAR

| Наблюдение HAR | Вывод |
|---|---|
| 56× `POST /api/v1/chart/data` → 200 | эндпоинт **доступен** в браузерной сессии |
| 1× 202 + успешный опрос `qc-…` | асинхронный режим работает, результат отдаётся |
| 42 `filter_select` с `row_limit: 2000` | значения колонок реально получаются из данных |
| 4 агрегатных чарта (`table`, `echarts_area`, `pivot_table_v2`) | агрегаты по `3035` реально считаются |
| `POST /api/v1/dashboard/977/filter_state` → 403 (×2) при пустом `X-CSRFToken` | это CSRF-отказ, а не запрет RBAC |

**Ключевой вывод:** проба P22 из этапа 1.6.2 дала 401 не потому, что `chart/data` запрещён
роли, а потому что запрос шёл без валидной сессии/CSRF (и, судя по коду
`src/phase1-6-2/recheck.ts`/`probe.ts`, без корректного браузерного контекста).
Формулировка «chart_data недоступен» в артефактах 1.6.2/1.7/1.8 — **опровергнута** фактом.
При этом `sql_lab` = 403 и `databases count=0` HAR не проверяет: там нет ни одного
обращения к `/api/v1/sqllab/*` и `/api/v1/database/`, поэтому эти два ограничения
остаются в силе.

### 3.3 Сверка объектов

| Проверка | Результат |
|---|---|
| Датасеты из HAR (39) присутствуют в локальном каталоге (3 778) | **39 / 39** |
| `slice_id` из HAR (6: 20161, 20403, 20623, 20624, 20404, 20405) в `charts_inventory.json` (19 928) | **6 / 6** |
| Дашборд 977 / slug `services_lite` | есть локально: «Статистика по заказам в разрезе сервисов лёгкая версия», 23 чарта, 3 датасета |
| Native-фильтры в `filter_state` | 54 шт.; локально для 977 — **54 строки**; 44 из них подтверждены по `dataset_id + column` |
| Локальные фильтры, не задействованные в сессии | 8 (в т.ч. 2 `filter_groupby`, 5 `filter_select`, 1 `filter_time`) |

Каталог метаданных и фильтров собран корректно: расхождений по идентификаторам не найдено.

### 3.4 Сверка полноты полей (главный пробел)

| Проверка | Результат |
|---|---|
| Датасеты, у которых **все** поля из HAR есть локально | **8 из 39** |
| Датасеты, у которых поля из HAR **отсутствуют** локально | **31 из 39** |
| Локально датасетов без колонок вообще | **3 111 из 3 778** (P2 — 2 637, OUT_OF_SCOPE — 470, P1 — 4) |
| Колонок в локальном каталоге | 17 216 (только 667 датасетов) |
| Метрик в локальном каталоге | 9 472 |

Примеры: `3035 darkstore_time_click` — локально 165 колонок и 417 метрик, но **11 метрик,
используемых в HAR** (`qty_orders_delivered`, `share_delivered_taxi`, `sum_with_bonuses`…),
в локальном `dataset_metrics.csv` не найдены. Для 30 «фильтровых» датасетов
(`*_f`, `*_filter`) локальных колонок нет вообще, а HAR даёт их имена
(`shopno`, `night`, `senior`, `delivery_type_group`, …).

Причина ясна из кода: `src/phase1-6-2/sync.ts` грузит детали только для P0+P1
(671 из 3 778) и только те поля, которые вернул сервер. HAR закрывает часть этих пробелов
**по именам полей**, но не даёт ни типов, ни значений.

## 4. Пригодность текущей системы к переиспользованию

### 4.1 Что можно переиспользовать как есть

| Компонент | Где | Готовность |
|---|---|---|
| Конфигурация и `.env`-контракт (`SUPERSET_URL/USERNAME/PASSWORD`) | `src/config.ts` | готово |
| Логин + JWT (`POST /api/v1/security/login`) | `src/superset.ts`, `src/phase1-6/client.ts`, `src/phase1-6-2/bulk.ts` | готово |
| Получение CSRF (`GET /api/v1/security/csrf_token/`) | там же | готово |
| Rison-пагинация list-эндпоинтов, сверка `count`/уникальности ID | `src/superset.ts: listFull`, `src/phase1-6-2/sync.ts: listResource` | готово |
| Ограничение конкурентности и ретраи 401/429/5xx | `BulkClient.pool/get`, `SupersetClient.requestWithRetry` | готово |
| Клиент деталей датасета | `phase1-6/client.ts:165`, `phase1-6-2/sync.ts:332` | готово (но без `q=`) |
| Модель хранения локальной копии | `src/store.ts` (SQLite `objects`/`relations`), `reports/phase-01-6-2/*.json` | частично |

### 4.2 Чего в системе нет — и что нужно добавить

1. **Клиента `chart/data`.** Ни один из трёх клиентов не отправляет POST на `/api/v1/chart/data`.
   В репозитории это только разовая проба в `src/phase1-6-2/probe.ts`, `recheck.ts`,
   `src/phase1-6/sqllab-diag.ts` — и она была признана неуспешной.
2. **Обработки асинхронного потока 202 → GET `/api/v1/chart/data/{key}`.** В
   `src/phase1-6/client.ts` есть похожий механизм, но только для SQL Lab
   (`/api/v1/sqllab/results/?key=…`), к `chart/data` он не применим.
3. **CSRF для POST.** `SupersetClient.getCsrf()` и `SqlLabClient.getCsrf()` токен получают,
   но `BulkClient` его не запрашивает вовсе, а POST-пробы 1.6.2, судя по HAR, шли с пустым
   `X-CSRFToken` — именно это дало 403 на `filter_state`.
4. **Сохранения тел ответов.** Ни один клиент не сохраняет ответы данных: локальная копия
   собрана из GET-метаданных. Для наполнения «фактическими значениями» нужен отдельный
   слой записи (сейчас `ACTUAL_VALUES = 0`).
5. **Реплеера HAR.** Разбора HAR в репозитории нет вообще (поиск по `*.md` и `src/` не находит
   ни `HAR`, ни `.har`).
6. **Правильной формы запроса деталей датасета.** Браузер использует
   `GET /api/v1/dataset/{id}?q=(columns:!(columns.column_name,…,sql,table_name))`;
   репозиторий — `GET /api/v1/dataset/{id}` без `q`. Результат совместим, но браузерный
   вариант дешевле (177 КБ против полного ответа на «широких» датасетах).

### 4.3 Прямое воспроизведение `har.har` невозможно

| Что нужно для replay | Есть в HAR |
|---|---|
| Валидная сессия (cookie `session`) | нет |
| `Authorization: Bearer …` | нет |
| Непустой `X-CSRFToken` | нет (пустой) |
| Тела ответов для сверки | нет |
| `Referer`/`Origin` | есть |
| Полные payload-ы запросов | **есть** |

Вывод: HAR можно использовать как **источник проверенных запросов** (что и как спрашивать),
но не как **источник данных** (что ответили). Для получения данных нужна отдельная
аутентифицированная сессия (`SUPERSET_USERNAME`/`SUPERSET_PASSWORD` в `.env`;
в репозитории `.env` отсутствует, есть только `.env.example`).

## 5. Что даст HAR при правильном использовании

### 5.1 Немедленно, без сети

- **44 подтверждённых таргета фильтров** (`dataset_id` + `column`) с полными payload-ами —
  проверка `dashboard_filters.json` без обращения к Superset.
- **Имена полей** для 31 датасета, у которых локально нет колонок (в т.ч. 4 датасета P1
  без деталей).
- **11 метрик `3035`**, отсутствующих в локальном `dataset_metrics.csv`.
- **Готовый реестр запросов для воспроизведения**: 57 payload-ов с датасетом, полями,
  метриками, фильтрами, `row_limit` и `time_range`.

### 5.2 После воспроизведения (нужна сессия)

- **Значения колонок из данных** для 44 колонок (`filter_select`, `row_limit: 2000`) —
  это переход `FILTER_VALUES` → `ACTUAL_VALUES`.
- **Агрегаты** по `3035` (4 чарта) и проверка свежести `max(date_update)` по `5979`.
- Возможность точечно снять агрегаты по 6 приоритетным датасетам этапа 1.6
  (5939, 7802, 7712, 7021, 3466, 2339) **без SQL Lab** — если для них удастся собрать
  валидные `chart/data` payload-ы (в HAR их нет: этих датасетов в сессии не было).

### 5.3 Ограничения, которые HAR не снимает

- `sql_lab` (403) и `databases count=0` — не проверялись, остаются блокерами
  для произвольного SQL, JOIN-проверок, `EXPLAIN`, кардинальностей и NULL-долей.
- `chart/data` даёт только то, что позволяет `form_data`: агрегаты и значения по колонкам,
  но не свободные JOIN-ы между датасетами.
- PII: `filter_select` по колонкам типа `courier`, `senior`, `leader` может вернуть
  персональные значения — нужен фильтр по политике `docs/phase-01-5/19_security_and_pii.md`.

## 7. Рекомендации

### Вариант A (рекомендуется): HAR как карта, отдельный сбор как источник данных

1. Оставить существующий синхронизатор метаданных (`src/phase1-6-2/sync.ts`) как есть —
   он подтверждён и корректен по идентификаторам.
2. Добавить `src/phase1-9/chart-data.ts` — клиент `POST /api/v1/chart/data` с:
   - логином и **обязательным** CSRF (`X-CSRFToken`), `Referer` = базовый URL;
   - обработкой 202 → опрос `GET /api/v1/chart/data/{key}` до `200`/таймаута;
   - сохранением тела ответа в `reports/…/chart_data/<dataset_id>__<query_hash>.json`
     с `query_hash` от payload-а (идемпотентность и дедупликация);
   - ограничением конкурентности (2–4) и `row_limit` по политике;
   - классификацией `ACTUAL_VALUES` только для успешных ответов.
3. Реплеер HAR (`tools/har-replay.ts`): читает `har.har`, выбирает payload-ы `chart/data`,
   подставляет сессию, выполняет, пишет результат и `execution_log.json`.
4. Расширить охват деталей датасетов: снимать `?q=(columns:!(…))` для датасетов,
   встречающихся в HAR и в фильтрах, включая P2/OUT_OF_SCOPE, у которых сейчас нет колонок.
5. Зафиксировать в `GAP-020` разделение: `chart_data` — AVAILABLE (по факту HAR),
   `sql_lab` — FORBIDDEN (не проверялся HAR, остаётся блокером).

### Вариант B: только HAR без сети

Использовать HAR как справочник таргетов и payload-ов. Даёт проверку фильтров и имён полей,
но **не даёт** `ACTUAL_VALUES`. Для аналитической работы этого недостаточно.

### Вариант C (не рекомендуется): HAR как основной метод синхронизации

Не работает: 0 тел ответов, 0 cookie, пустой CSRF. Любая попытка «наполнить локальную копию
из HAR» без сети даст только имена объектов и запросов, но не данные.

## 8. Ограничения этого аудита

- Использован только файл `har.har`; повторная запись трафика не выполнялась.
- Сетевые запросы к Superset не выполнялись, `chart/data` не воспроизводился —
  вывод «эндпоинт доступен» основан на статусах 200/202 в HAR, а не на собственной пробе.
- Состав HAR ограничен одной сессией одного дашборда (977): 39 датасетов из 3 778.
- Причины 401 в пробе P22 этапа 1.6.2 восстановлены по коду и HAR косвенно; точная причина
  (RBAC роли против отсутствия сессии) требует отдельной проверки с реальной аутентификацией.
- В HAR нет запросов к `/api/v1/sqllab/*` и `/api/v1/database/`, поэтому статус SQL Lab
