# Контракт стратегии прогнозирования

**Статус:** действующий (Stage 3.4.1) · **Версия контракта:** `strategy/v1` · **Дата:** 2026-11-23
**Область:** магазин `7745`, срез `20624`, метрика `qty_orders_delivered` → `delivered_orders_daily`

Настоящий контракт определяет, что именно прогнозируется и по каким правилам. Он обязателен для всех последующих моделей и экспериментов; отклонение допускается только через новую версию контракта.

---

## 1. Объект прогнозирования

| Параметр | Значение |
|---|---|
| Целевой показатель | `delivered_orders_daily` (исходная метрика `qty_orders_delivered`) |
| Тип задачи | univariate time series forecasting |
| Объект | один даркстор (`shop_no = 7745`) |
| Гранулярность | один календарный день |
| Единица измерения | заказы (шт.) |
| Часовой пояс | Europe/Moscow |
| Целевая переменная | количество доставленных заказов за календарный день |

В целевую переменную **запрещено** включать денежные метрики, численность курьеров, загрузку слотов, долю отмен и любые другие показатели. Использование дополнительных факторов — предмет отдельных будущих этапов, каждый из которых обязан сохранять целевой показатель неизменным.

**Статус бизнес-семантики:** `PROVISIONAL`. Формула источника —
`COUNT(DISTINCT IF(status_name = 'Успешно завершен', COALESCE(id_general, id_order), NULL))`.
Повышение статуса до `CONFIRMED` без письменного подтверждения владельца процесса **запрещено**.

## 2. Горизонты прогнозирования

| Горизонт | Обозначение | Назначение |
|---|---|---|
| 1 день | `h=1` | краткосрочное оперативное планирование |
| 3 дня | `h=3` | краткосрочное планирование |
| 7 дней | `h=7` | недельное планирование |
| 14 дней | `h=14` | двухнедельное планирование |

Требования:

1. Каждый горизонт оценивается и публикуется **отдельно**.
2. Объединение горизонтов в одну метрику запрещено без явного указания цели агрегирования; такое объединение не может использоваться для выбора модели.
3. Расширение списка горизонтов возможно только новой версией контракта с указанием назначения.

## 3. Термины времени

| Термин | Определение |
|---|---|
| `origin_date` | последняя дата, на которую модели разрешено использовать фактические данные (включительно) |
| `target_date` | дата, для которой строится прогноз |
| `horizon_step` | число календарных шагов от `origin_date` до `target_date`; `horizon_step = target_date − origin_date` в днях, всегда `> 0` |
| `forecast_created_at` | момент фактического построения прогноза (UTC, ISO-8601) |
| `training_window` | диапазон наблюдений, доступных модели: `[first_date, origin_date]` |

**Основное правило:** для прогноза на шаг `h` модель может использовать только информацию, доступную на соответствующем `origin_date`. Использование фактического значения `target_date` или любых сведений, появившихся позже `origin_date`, запрещено.

Дополнительно фиксируется: горизонт `h=7` при контракте `weekly_seasonal_naive` требует фактического значения на дату `origin_date`, поэтому модель на этом шаге тождественна `naive_yesterday` (установлено в Stage 3.3.6). Это свойство контракта модели, а не дефект данных.

## 4. Стратегия выбора модели

- Одна универсальная модель для всех горизонтов **не назначается**. Выбор выполняется независимо для `h=1`, `h=3`, `h=7`, `h=14`.

Стартовые кандидаты (рабочая гипотеза, не production-конфигурация):

| Горизонт | Кандидат | Основание (Stage 3.3.6, режим `step-exact`, `min_train=28`) |
|---|---|---|
| 1 | `naive_yesterday` / `rolling_7_day_mean` | MAE 100.84 против 100.80 — различие в пределах шума |
| 3 | `rolling_7_day_mean` | MAE 114.65 против 122.61 / 135.62 |
| 7 | `naive_yesterday` | MAE 123.13; `rolling_7_day_mean` — 137.42 |
| 14 | `naive_yesterday` | MAE 154.04 против 160.58; `weekly_seasonal_naive` недоступен |

Правила:

1. Эти результаты — исходная точка сравнения, **не** доказательство производственного превосходства.
2. Победитель не закрепляется по единственному отчёту.
3. Для каждого горизонта сравнивается кандидат с действующим лучшим baseline.
4. Сравнение выполняется на сопоставимой выборке (см. контракт оценки).
5. Улучшение признаётся только по правилам контракта выбора модели.

## 5. Допустимые изменения без новой версии контракта

- добавление новых кандидатов-моделей;
- добавление новых горизонтов — **нет**, требуется новая версия;
- проведение sensitivity-экспериментов, не меняющих основной режим;
- уточнение формулировок документации без изменения правил.

## 6. Изменения, требующие новой версии контракта

- изменение целевого показателя или единицы измерения;
- изменение горизонта или шага прогноза;
- изменение правил доступа к данным;
- изменение основного режима оценки;
- изменение правил выбора модели;
- повышение статуса бизнес-семантики.

## 7. Ограничения этапа

- Контракт не содержит новых моделей и не изменяет baseline Stage 3.3.
- Контракт не подтверждает бизнес-смысл `date_supply`, правила перерасчётов, возвратов и корректировок — эти пункты остаются `UNCONFIRMED`.
- Настоящий документ не является разрешением на производственное использование прогнозов.
