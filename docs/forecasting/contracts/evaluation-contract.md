# Контракт оценки (evaluation contract)

**Статус:** действующий (Stage 3.4.1) · **Версия контракта:** `evaluation/v1` · **Дата:** 2026-11-23

Документ формализует правила формирования оценочных выборок и сопоставимости моделей. Он является основным документом Stage 3.4.1.

---

## 1. Основной режим

```text
evaluation_mode = step-exact
primary_min_train_days = 28
sensitivity_min_train_days = 21
horizons = [1, 3, 7, 14]
```

- `step-exact` — **основной** режим публикации результатов: горизонт `h` оценивается ровно на шаге `h`.
- `cumulative` — **только справочный** режим: учитываются шаги `1…h`; результат нельзя подписывать как точное качество прогноза на `h`-й день.
- Любая таблица обязана содержать колонку `evaluation_mode` и `min_train_days`.

## 2. Формальное определение оценочного наблюдения

- Ключ наблюдения:

```text
(origin_date, target_date, horizon_step)
```

Для горизонта `h` в основную выборку включаются записи, удовлетворяющие **всем** условиям:

1. `horizon_step = h` (для режима `step-exact`).
2. Модель имеет допустимый прогноз (`status = ok`, значение конечно).
3. Фактическое значение `actual` доступно и конечно.
4. Соблюдено ограничение обучающего окна: число доступных наблюдений на `origin_date` не меньше `min_train_days`.
5. Нет признаков использования будущих данных: `max(дата истории) ≤ origin_date < target_date`.
6. Наблюдение прошло правила качества: отсутствуют `NaN`, `Infinity`, дубликаты ключа.

Запрещено объединять наблюдения так, чтобы терялось происхождение прогноза (модель, origin, шаг, режим).

## 3. Сопоставимость моделей

- Прямое сравнение выполняется на **общих парах** `(origin_date, target_date)`. Для пары моделей A и B должны совпадать:

- `origin_date`;
- `target_date`;
- `horizon_step`;
- `actual`;
- правила формирования обучающего набора (`min_train_days`, доступная история).

Правила:

1. Если модель не имеет прогноза для пары, она **не получает** подставленное, интерполированное или нулевое значение.
2. Публикуются: число прогнозов каждой модели, число общих наблюдений, число исключённых наблюдений и причины исключения.
3. Сравнение MAE, рассчитанных на существенно разных выборках, **не** маркируется как строгое парное сравнение (см. статус `INCONCLUSIVE` в контракте выбора модели).
4. Общий набор нескольких моделей формируется только по моделям, имеющим прогноз на оцениваемом шаге; состав общего набора документируется.

**Отдельное правило интерпретации (зафиксировано по итогам приёмки Stage 3.3.6):** практическое преимущество победителя измеряется относительно **ближайшего конкурента**, а не относительно худшей модели. Для этого публикуются величины:

```text
margin_to_runner_up = MAE_best / MAE_second_best − 1
margin_to_worst      = MAE_worst / MAE_best − 1        (справочно)
margin_vs_baseline   = (MAE_candidate − MAE_baseline) / MAE_baseline
```

Численное определение «неразличимости» (`NO_MATERIAL_DIFFERENCE`) вводится отдельной политикой практической значимости (см. контракт выбора модели, раздел 3) и в Stage 3.4.1 не устанавливается.

## 4. Режим cumulative

```text
для горизонта h учитываются шаги 1 … h
```

Обязательно:

- в отчётах указывать `evaluation_mode = cumulative`;
- явно пояснять, что оценка объединяет несколько шагов;
- не использовать cumulative для выбора модели и для сравнения горизонтов.

## 5. Доступность модели

| Статус | Значение | Считается ошибкой модели |
|---|---|---|
| `AVAILABLE` | модель имеет допустимый прогноз | нет |
| `NOT_AVAILABLE` | по своему контракту модель не может выдать прогноз на данном шаге | **нет** |
| `INVALID` | прогноз должен был быть выдан, но нарушает технические или методологические требования | да |

Требования:

1. `NOT_AVAILABLE` не считается ошибкой и не маскируется под `INVALID`.
2. `INVALID` не маскируется под `NOT_AVAILABLE`; наблюдение исключается из метрик, причина фиксируется.
3. Отсутствующий прогноз **не заменяется нулём** и не интерполируется.
4. Для `weekly_seasonal_naive` сохраняется ограничение Stage 3.3.6: на шаге `h=14` отсутствует необходимое значение `target − 7` на момент `origin` → `NOT_AVAILABLE`.

## 6. Минимальная длина обучения

| Режим | Значение | Назначение |
|---|---|---|
| основной | `min_train_days = 28` | основная публикация результатов |
| sensitivity | `min_train_days = 21` | анализ чувствительности |

Запрещено:

- объединять результаты двух режимов в одной таблице;
- выбирать более выгодный результат без указания режима;
- подменять основной режим sensitivity-режимом;
- менять `min_train_days` в ходе эксперимента без нового идентификатора конфигурации.

## 7. Связь с реализацией

| Правило контракта | Реализация |
|---|---|
| `step-exact` / `cumulative` | `src/forecasting/analytics/backtesting/rolling-origin.ts` (`evaluationMode`, фильтр `record.step === horizon`) |
| `NOT_AVAILABLE` | `notAvailable[]` в результате backtesting |
| проверка утечки | `leakage` (условия `lastHistoryDate ≤ origin < targetDate`) |
| основной режим | `DEFAULT_MIN_TRAIN = [28, 21]`, первый элемент — основной |
| публикация режимов | `src/forecasting/analytics/backtesting/reports.ts` |

## 8. Ограничения

- Контракт не изменяет данные, формулы baseline и результаты Stage 3.3; он определяет только правила оценки. Числовые пороги практической значимости сознательно не установлены.
