# Контракт отчётности экспериментов (experiment reporting contract)

**Статус:** действующий (Stage 3.4.1) · **Версия контракта:** `reporting/v1` · **Дата:** 2026-11-23

Документ определяет минимальный набор информации для публикации любого эксперимента и правила разделения результатов.

---

## 1. Обязательные поля отчёта

| № | Поле | Пояснение |
|---|---|---|
| 1 | название эксперимента | человекочитаемое |
| 2 | уникальный идентификатор | `experiment_id` |
| 3 | дата запуска | ISO-8601 (UTC) |
| 4 | версия кода | HEAD / тег |
| 5 | версия модели | `model_version` |
| 6 | конфигурация | `config_hash` и параметры |
| 7 | checksum набора данных | checksum содержимого canonical CSV |
| 8 | целевая метрика | `delivered_orders_daily` |
| 9 | период данных | `from … to` |
| 10 | список горизонтов | `[1, 3, 7, 14]` |
| 11 | режим оценки | `step-exact` / `cumulative` |
| 12 | `min_train_days` | 28 (основной) / 21 (sensitivity) |
| 13 | количество прогнозов | по модели и горизонту |
| 14 | количество общих наблюдений | по общему набору |
| 15 | метрики | `MAE`, `RMSE`, `WAPE`, `Bias`, дополнительные |
| 16 | сравнение с baseline | `margin_to_runner_up`, `margin_vs_baseline`, абсолютная и относительная разница |
| 17 | ограничения | известные ограничения интерпретации |
| 18 | известные проблемы | дефекты, инциденты, пробелы |
| 19 | итоговый статус | `BETTER` / `WORSE` / `NO_MATERIAL_DIFFERENCE` / `INCONCLUSIVE` / `NOT_AVAILABLE` / `INVALID` |

## 2. Разделение результатов

- В отчётах обязательно различаются:

1. **Основной результат** — `evaluation_mode = step-exact`, `min_train_days = 28`.
2. **Sensitivity analysis** — `evaluation_mode = step-exact`, `min_train_days = 21`.
3. **Справочные cumulative-результаты** — `evaluation_mode = cumulative`.
4. **Недоступные модели** — `NOT_AVAILABLE` с причиной.
5. **Некорректные эксперименты** — `INVALID` с причиной.
6. **Эксперименты, не прошедшие проверку сопоставимости** — `INCONCLUSIVE`.

Правила:

- основной результат всегда визуально и текстово отличим от дополнительных исследований;
- три режима не объединяются в одну таблицу без явного обозначения;
- значения sensitivity не используются в выводах об основном результате;
- каждая таблица содержит колонки `evaluation_mode` и `min_train_days`.

Идентификаторы режимов для текущего проекта:

```text
PRIMARY:     evaluation_mode = step-exact, min_train_days = 28
SENSITIVITY: evaluation_mode = step-exact, min_train_days = 21
REFERENCE:   evaluation_mode = cumulative
```

## 3. Обязательные счётчики покрытия

```text
origins_total, origins_evaluated,
forecasts_expected, forecasts_generated, forecasts_missing,
actuals_missing, common_evaluation_count
```

Правила:

1. Пропущенный прогноз не заменяется нулём.
2. Каждое исключение имеет причину и попадает в счётчик.
3. `common_evaluation_count` публикуется с формулой расчёта: число пар `(origin, target)` на горизонт, где у всех доступных моделей есть прогноз и есть факт. При агрегировании по горизонтам указывается, что это **сумма**, а не число уникальных дат.

## 4. Обязательные формулировки

- Результат на горизонте `h` в режиме `cumulative` не называется «качеством прогноза на h-й день».
- При отсутствии численного порога значимости запрещены формулировки вида «модель лучше» без указания `margin_to_runner_up`; при малом отрыве используется формулировка «модели неразличимы на доступной истории».
- `NOT_AVAILABLE` не называется ошибкой модели.
- Прогнозы, полученные при статусе семантики `PROVISIONAL`, помечаются как технические и не используются для бизнес-обещаний.

## 5. Хранение и преемственность

1. Предыдущие версии отчётов сохраняются в `archive/` соответствующего этапа, а не перезаписываются.
2. Изменение отчёта фиксируется отдельным документом с перечнем правок и причин.
3. Удаление отчётов запрещено.

- Контракт не вводит новых форматов хранения и не переписывает существующие отчёты Stage 3.1–3.3.6.
