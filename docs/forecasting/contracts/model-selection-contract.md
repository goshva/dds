# Контракт выбора модели (model selection contract)

**Статус:** действующий (Stage 3.4.1) · **Версия контракта:** `selection/v1` · **Дата:** 2026-11-23

Документ определяет, при каких условиях модель может быть допущена к сравнению и признана перспективнее baseline.

---

## 1. Обязательные условия допуска кандидата

- Кандидат допускается к оценке качества только при выполнении **всех** условий:

| № | Условие | Проверка |
|---|---|---|
| 1 | документированная формула или описание алгоритма | наличие спецификации модели |
| 2 | фиксированная конфигурация | `config_hash` |
| 3 | воспроизводимый запуск | повторный прогон даёт идентичный результат |
| 4 | отсутствие доступа к будущим данным | `assertNoFutureData`, leakage-проверка |
| 5 | корректные даты прогнозов | `target_date > origin_date`, шаг совпадает с горизонтом |
| 6 | отсутствие `NaN` / `Infinity` | `ensureFinite`, `validateMetricSet` |
| 7 | документированное поведение при недостатке истории | статус `NOT_AVAILABLE` с причиной |
| 8 | определённые правила обработки пропусков | отсутствие интерполяции и подстановки нуля |
| 9 | сравнение с baseline на сопоставимой выборке | общие пары `(origin_date, target_date)` |
| 10 | идентификатор версии алгоритма и конфигурации | `model_id`, `model_version` |

Нарушение любого условия → модель **не допускается** к оценке качества (статус `INVALID`).

## 2. Сравнение с baseline

- Для каждого горизонта:

1. Кандидат сравнивается минимум с действующим лучшим baseline.
2. Результаты **всех** доступных baseline сохраняются.
3. В сравнение включаются: `MAE`, `RMSE`, `WAPE`, `Bias`, число прогнозов, число общих наблюдений, абсолютная разница MAE, относительное изменение MAE, список исключённых наблюдений.

```text
relative_mae_change = (candidate_mae − baseline_mae) / baseline_mae × 100
```

Отрицательное значение — улучшение относительно baseline. При `baseline_mae = 0` относительное изменение не рассчитывается → `NOT_AVAILABLE`.

Обязательно публикуется `margin_to_runner_up` — преимущество относительно **ближайшего конкурента**, а не относительно худшей модели (см. контракт оценки, раздел 3).

## 3. Статусы результата сравнения

| Статус | Значение |
|---|---|
| `BETTER` | улучшение по основной метрике на сопоставимой выборке |
| `WORSE` | ухудшение по основной метрике |
| `NO_MATERIAL_DIFFERENCE` | различие недостаточно для обоснованного практического вывода |
| `INCONCLUSIVE` | недостаточно данных или нарушена сопоставимость |
| `NOT_AVAILABLE` | сравнение невозможно (нет прогнозов / нет baseline) |
| `INVALID` | кандидат нарушил обязательные условия допуска |

**Важно:** универсальное численное определение `NO_MATERIAL_DIFFERENCE` на этапе Stage 3.4.1 **не устанавливается**. Для его введения потребуется отдельная политика практической значимости, основанная на бизнес-требованиях и статистической оценке (например, сравнение разности ошибок на общих парах с учётом её разброса). До появления такой политики статус присваивается экспертно и обязательно сопровождается величиной `margin_to_runner_up`.

## 4. Победитель определяется отдельно для горизонта

- Допустима конфигурация:

```text
h=1  -> model_A
h=3  -> model_B
h=7  -> model_C
h=14 -> model_D
```

Автоматический выбор одной модели для всех горизонтов запрещён.

## 5. Условия производственного назначения

- Статус `PRODUCTION_APPROVED` невозможен до одновременного выполнения:

1. подтверждённая бизнес-семантика (снятие `PROVISIONAL`);
2. достаточная история (обоснованный объём, покрывающий сезонный цикл);
3. воспроизводимый backtesting на утверждённом контракте;
4. стабильность результата (в том числе на sensitivity-режиме и на нескольких периодах);
5. отсутствие существенных проблем с `Bias`;
6. подтверждение владельцем продукта.

До этого момента любая модель имеет статус не выше «кандидат, показавший лучший результат на доступной истории».

## 6. Запрет подгонки под тест

1. Подбор гиперпараметров по итоговой тестовой выборке запрещён.
2. Изменение формулы после просмотра результата требует нового идентификатора эксперимента.
3. Неудачные эксперименты не скрываются и не удаляются.
4. Публикация только лучшего запуска запрещена.
5. Все проверенные конфигурации фиксируются.
6. Исследовательские эксперименты отделяются от итоговой оценки.

## 7. Связь с реализацией

| Правило | Реализация / статус |
|---|---|
| отсутствие доступа к будущему | `assertNoFutureData` (baselines/types.ts) |
| leakage-проверка | `leakage` в результате backtesting |
| `NOT_AVAILABLE` | `notAvailable[]` |
| `INVALID` | `validateMetricSet`, `ensureFinite` (проверка конечности) |
| сопоставимость | `commonStepMetrics` (общие пары) |
| воспроизводимость | `reproducibility.checksum`, сравнение двух прогонов |

## 8. Ограничения

- Контракт не назначает production-модель, не вводит порогов значимости и не изменяет baseline Stage 3.3. Статус бизнес-семантики остаётся `PROVISIONAL`.
