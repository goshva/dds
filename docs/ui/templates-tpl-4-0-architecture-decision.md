# TPL-4.0 — архитектурное решение по источнику разметки

> **Архитектурная поправка TPL-4.5.** Каталог `src/web/templates/partials/` удалён в TPL-4.4.
> Production HTML формируют `src/web/components/` и `src/web/pages/`; экранирование — `src/web/lib/format.ts`;
> актуальная документация архитектуры — `src/web/templates/README.md`; эталоны страниц — `docs/ui/reference/`
> (генератор `tools/reference/`). Исторические результаты ниже не изменялись.

## 1. Постановка

- Разметка компонентов существует в трёх местах: TypeScript-компоненты (исполняются), HTML partials (статическая спецификация), reference-страницы (рукописные эталоны). Дублирование подтверждено: 8 расхождений (R-1…R-8), из которых 7 означают, что partials **нельзя** использовать как источник разметки без переписывания компонентов.

Требуется выбрать единственный источник истины, не ухудшив безопасность, типизацию и визуальный паритет.

## 2. Вариант A — TypeScript как источник истины

Компоненты остаются единственным источником разметки; reference-страницы и partials **генерируются** из них с контролируемыми фикстурами.

- безопасность: сохраняется полностью (экранирование остаётся в `escapeHtml`/`safeHref`/`trusted`);
- типизация: `props` остаются строгими TS-интерфейсами, компилятор проверяет фикстуры;
- производительность: runtime не меняется;
- зависимости: не требуются (Bun + существующие модули);
- поддержка: изменение разметки в одном месте — компоненте;
- тестируемость: генерация даёт детерминированный артефакт, пригодный для snapshot-тестов;
- визуальный паритет: эталон по построению совпадает с компонентом;
- сборка: генератор — отдельный скрипт (`bun run …`), Vite не затрагивается;
- ограничение: генерация выполняется вне браузера, поэтому интерактивные состояния по-прежнему показываются статически.

## 3. Вариант B — partials как источник разметки с компиляцией при сборке

Partial компилируется в функцию `props → html`, компоненты становятся адаптерами данных.

Что требуется по факту кода:

- поддержать условия, циклы, вложенные partials (в `data-table.html` вложенность `rows → cells`, в `search`-подобных блоках — инвертированные ветки);
- перенести вычисления в адаптеры: `cells[]` для таблицы, `path`/`cssClass` для графиков, `x`/`y`/`barWidth`/`barHeight`, `points`, `skeletons[].width`, `badgeClass`, `statusClass`;
- создать 3 отсутствующие функции (`sidebar-brand`, `sidebar-nav`, `forecast-mode-switcher`) и переписать `historyFilters`;
- сохранить закрытый перечень доверенных слотов и не дать компилятору трактовать произвольные значения как разметку.

Вывод: это не «ограниченный компилятор», а полноценная смена модели рендеринга с переписыванием 8 компонентов и 2 страниц. Риск регрессии высокий, объём — вне рамок одной задачи.

## 4. Вариант C — исполнение шаблонов в runtime

Потребует зависимости (Mustache-совместимый движок или собственный интерпретатор), увеличит бандл, добавит путь для XSS, лишит `props` типовой проверки, усложнит тесты и не даст пользовательской ценности: интерфейс — статическая read-only панель без пользовательских шаблонов.

Дополнительный риск: экранирование пришлось бы реализовывать или настраивать повторно, что прямо противоречит требованию «не ухудшить XSS-защиту».

## 5. Вариант D — гибридная архитектура

Разметка компонентов централизуется в TypeScript, композиция страниц и подготовка данных остаются в TypeScript, а partials переводятся в **производный документационный артефакт**, генерируемый из компонентов.

Это вариант A, дополненный судьбой partials: они перестают поддерживаться вручную и не могут «разъехаться» с кодом.

## 6. Сравнение

| Критерий | A | B | C | D |
|---|---|---|---|---|
| Безопасность | не меняется | риск при переносе экранирования | риск (новый путь обработки строк) | не меняется |
| Типизация props | полная | частичная (шаблон вне типов) | отсутствует | полная |
| Runtime-накладные | нет | нет | есть (парсинг/рендер) | нет |
| Новые зависимости | не нужны | не нужны (свой компилятор) | нужны | не нужны |
| Объём изменений production | 0 | 8 компонентов + 2 страницы | 8 компонентов + main | 0 |
| Риск расхождения | устраняется генерацией | устраняется | устраняется | устраняется |
| Тестируемость | snapshot-паритет | тесты компилятора | тесты движка | snapshot-паритет |
| Совместимость с Vite | полная | требует шага сборки | требует плагина | полная |
| Бизнес-логика в HTML | нет | частично (адаптеры) | нет, но логика в шаблонах растёт | нет |
| Правило ≤200 строк | сохраняется | нарушается (адаптеры) | сохраняется | сохраняется |

## 7. Рекомендация

**Принять вариант A/D: TypeScript-компоненты — единственный источник истины; partials и reference-страницы — производные артефакты.**

Границы ответственности:

| Слой | Ответственность |
|---|---|
| `src/web/components/**` | единственная разметка атомарных компонентов, экранирование, `TrustedHtml`, перечислимые классы |
| `src/web/pages/**`, `main.ts` | композиция страниц, подготовка данных, состояния загрузки/ошибок, маршрутизация |
| `src/web/lib/format.ts` | примитивы безопасности и форматирования (без изменений) |
| генератор (новый, вне production) | сборка reference-страниц и производных partials из компонентов с фикстурами |
| `docs/ui/reference/**` | результат генерации: HTML-эталоны с маркировкой синтетических данных |
| `src/web/templates/partials/**` | документационный контракт; при принятии плана — генерируемый артефакт, не поддерживаемый вручную |

Причины отказа: B — требует переписывания production-компонентов и повторной реализации границ escaping; C — новая зависимость и новый класс уязвимостей без пользовательской выгоды; чистое сохранение текущего состояния — не снижает риск расхождения (R-1…R-7 существуют уже сейчас).

## 8. Открытые вопросы

1. Удалять ли `src/web/templates/partials/**` после появления генератора или оставить как человекочитаемый контракт (решение — отдельным этапом, по умолчанию — оставить и пометить как производные).
2. Где размещать генератор: `tools/` (утилиты проекта) или `docs/ui/reference/tools/` (артефакты документации). Предпочтительно `tools/`, чтобы переиспользовать проверки и не смешивать с эталонами.
3. Нужны ли фикстуры на каждую страницу отдельно или общий набор с переопределениями (влияет на объём поддержки).
4. Сохранять ли рукописные состояния (`loading`, `empty`, `error`) в эталонах после генерации: генератор может собирать их из существующих компонентов состояний.
5. Требуется ли snapshot-тест разметки компонентов (стабилизация HTML) до генерации — снижает шум диффов.

## 9. Технические риски рекомендуемого варианта

- генератор должен быть детерминированным (порядок ключей, отсутствие времени и случайности), иначе диффы эталонов будут шумными;
- фикстуры должны оставаться синтетическими и маркированными, чтобы не создать впечатление реальных показателей;
- генерация не должна попадать в production-сборку: только `bun run`-скрипт и каталог документации;
- правило ≤200 строк: генератор и фикстуры нужно разбить по модулям.
