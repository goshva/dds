## 1. Общая последовательность

| Подэтап | Содержание | Результат |
|---|---|---|
| TPL-4.1 | генератор reference-страниц из production-компонентов + фикстуры | 6 страниц генерируются детерминированно |
| TPL-4.2 | паритет partials и компонентов: генерация производных partials или тест соответствия | расхождения R-1…R-7 либо устранены, либо явно зафиксированы |
| TPL-4.3 | документация: контракт и README помечают partials как производные | нет ручных контрактов, расходящихся с кодом |
| TPL-4.4 | решение по удалению/депрекации partials (отдельное согласование) | единый источник разметки |

Порядок обязателен: генерация (4.1) предшествует изменению статуса partials (4.2–4.4).

## 2. TPL-4.1 — генератор эталонов

**Файлы в scope (новые):**

- `tools/reference/fixtures.ts` — синтетические данные на каждую страницу (≤200 строк);
- `tools/reference/render-page.ts` — сборка HTML-документа из вызовов `appShell`, `sidebar`, `topbar`, `pageHeader`, компонентов;
- `tools/reference/generate.ts` — запись шести страниц и индекса, детерминированный порядок;
- `tests/web/reference-generation.test.ts` — проверка детерминированности и структуры результата;
- `package.json` — скрипт `ui:reference` (изменение только этого файла, отдельным согласованием).

**Файлы в scope (изменяемые):** `docs/ui/reference/{index.html, pages/*.html, README.md}` — перезаписываются генератором.

**Файлы вне scope:** `src/web/components/**`, `src/web/pages/**`, `main.ts`, `routing.ts`, `styles/**`, `src/server/**`, `src/forecasting/**`, `data/**`, `src/web/templates/partials/**` (в 4.1), `diff.txt`.

**Требования к генератору:**

1. детерминированность: без времени, случайности и зависимости от порядка обхода файловой системы;
2. маркировка синтетических данных сохраняется (`REFERENCE DATA — NOT PRODUCTION DATA`);
3. семантика: `PROVISIONAL`, `[Н/Д]` вместо нуля, предупреждения не превращаются в ошибки;
4. использование тех же функций, что и production (`appShell`, `kpiGrid`, `dataTable`, `lineChart`, …) — никакой собственной разметки компонентов;
5. состояния (`loading`, `empty`, `error`, `not_available`) собираются из компонентов состояний, а не текстом.

## 3. TPL-4.2 — паритет partials

Два допустимых пути (выбор — по результату 4.1):

- **4.2а (предпочтительно):** генерировать partials из компонентов тем же генератором: для каждой функции формировать HTML с плейсхолдерами вместо значений (потребуется расширяемый способ подстановки, обсуждается отдельно);
- **4.2б:** сохранить partials как контракт и добавить тест соответствия: для каждой пары «компонент ↔ partial» проверять совпадение последовательности CSS-классов и структуры блоков при фиктивных props. Расхождения R-1…R-7 должны быть либо устранены в partial, либо явно перечислены в списке допустимых исключений.

Критерий: ни одно расхождение не остаётся недокументированным.

## 4. TPL-4.3 — документация

- `docs/ui/templates-contract.md`: пометить, что partials — производный артефакт; убрать формулировки, подразумевающие ручную поддержку;
- `src/web/templates/README.md`: указать команду генерации и правило «не править вручную»;
- новый отчёт `docs/ui/templates-tpl-4-x-report.md` по факту выполнения.

## 5. TPL-4.4 — решение по partials

Варианты: (а) оставить как документацию, (б) удалить после подтверждения паритета. Решение принимается отдельно; до него partials не удаляются и не редактируются вручную.

## 6. Тестовая стратегия

| Уровень | Проверка |
|---|---|
| Юнит | детерминированность генератора: два прогона дают идентичные файлы (сравнение контрольных сумм) |
| Контракт | фикстуры соответствуют TS-интерфейсам (компилятор) |
| Структура | наличие обязательных блоков, отсутствие плейсхолдеров в готовом HTML |
| Безопасность | отсутствие внешних ссылок и сетевых вызовов в эталонах; `safeHref` для навигации |
| Семантика | `PROVISIONAL`, `[Н/Д]`, предупреждения, отсутствие нулей вместо отсутствующих данных |
| Регрессия | `bun test tests/web tests/server`, `bunx tsc --noEmit`, `bun run ui:build` |
| Браузер | матрица 36 пар (6 страниц × 6 ширин) по методике TPL-3.1 |

## 7. Браузерная регрессия

Использовать методику TPL-3.1: Chrome for Testing через DevTools Protocol, ожидание готовности (шрифты, изображения, отсутствие skeleton, наличие контента), измерение геометрии (sidebar, content, topbar, KPI, таблицы, overflow, мобильная навигация). Для сгенерированных эталонов достаточно сравнения с текущими эталонами: геометрия обязана совпасть, отличия допустимы только в текстовых значениях фикстур.

## 8. Проверка данных

После каждого подэтапа: контрольные суммы `data/forecast/forecasting.sqlite`, `data/catalog.sqlite`, `data/shadow/7745/{forecasts.jsonl,reconciliations.jsonl,manifest.json}`, отсутствие `errors.jsonl`. Прогнозные операции не запускать. `diff.txt` не трогать.

## 9. Критерии rollback

- генерация не детерминирована (разные суммы при двух прогонах) — остановиться, не заменять эталоны;
- эталоны теряют маркировку синтетических данных или семантику `PROVISIONAL` — откат к предыдущим файлам из Git;
- требуется изменение production-разметки для генерации — остановиться и вынести отдельным решением;
- расхождение геометрии с текущими эталонами больше допустимого — не принимать, зафиксировать причину;
- любые изменения вне объявленного scope — остановка.

## 10. Критерии приёмки TPL-4.1

- [ ] шесть страниц и индекс воспроизводятся одной командой;
- [ ] повторный запуск даёт идентичные файлы (проверено контрольными суммами);
- [ ] разметка собрана из production-компонентов, собственной разметки компонентов нет;
- [ ] данные синтетические и маркированы;
- [ ] состояния представлены через компоненты состояний;
- [ ] тесты, `tsc` и сборка проходят;
- [ ] production-код, partials, CSS, API, routing, данные не изменены;
- [ ] отчёт создан, Git-история и `diff.txt` не изменены.

## 11. Риски и меры

| Риск | Мера |
|---|---|
| Шумные диффы эталонов | детерминированный порядок, отсутствие времени и случайности |
| Случайное попадание генератора в production-сборку | генератор только в `tools/`, ссылок из `src/web` нет |
| Расхождение фикстур с интерфейсами | фикстуры типизированы TS, проверяются компилятором |
| Потеря семантики предупреждений | тесты семантики в наборе проверок |
| Рост размера файлов | разбиение генератора и фикстур по модулям (≤200 строк) |
| Незамеченное изменение данных | проверка контрольных сумм после каждого подэтапа |

## 12. Что не делается в TPL-4.x

- перенос бизнес-логики в HTML;
- внедрение шаблонного движка в runtime;
- изменение production-разметки, CSS, API, маршрутизации, forecasting;
- удаление partials до отдельного решения;
- исправление замечаний вне области этапа (имя пакета, `diff.txt`, workflow runs).
