## 1. Назначение

- Раздел истории и аналитики: просмотр исторической динамики заказов магазина 7745 (canonical slice 20624), анализ по дням, оценка полноты ряда, происхождение и актуальность источника. UI показывает данные и их происхождение, не подменяет отсутствующие значения и не выполняет прогнозных расчётов.

## 5. Формулы показателей

| Показатель | Формула |
|---|---|
| `sum`, `average`, `max`, `min` | только по доступным (конечным) значениям выбранного периода |
| `calendarDays` | календарные дни **запрошенного** диапазона (UI-3.1), включая дни за границами доступной истории |
| `observationDays` | число точек с конечным значением |
| `missingDays` | `calendarDays − observationDays` (включая дни за границами данных) |
| `fillRatio` | `observationDays / calendarDays` (календарные дни = `days + gaps`) |
| `maxGapLength` | максимальная длина интервала подряд идущих пропусков |
| `rangeClamped` | `true`, если запрошенный диапазон выходит за доступную историю (частично) |
| `truncated` | `true`, если ответ обрезан `limit`; агрегаты при этом считаются по всему диапазону |

## 6. Правила NULL / 0

- `NULL ≠ 0`: отсутствующее значение показывается как `[Н/Д]`, не интерполируется и не заменяется средним;
- фактический ноль отображается как `0`;
- сервер отклоняет пустые и нечисловые значения canonical CSV (`DATA_SOURCE_CORRUPTED`), поэтому `nullValues = 0` — политика (`nullPolicy = REJECTED_AS_CORRUPTED`), а не пропуск полноты;
- график разрывает линию на отсутствующих наблюдениях (подпуть `M` вместо продолжения).

## 6.1. Календарная корректность (UI-3.1)

- `calendarDays` считается по запрошенному диапазону, а не по найденным точкам: неполный период не выглядит полным;
- диапазон, **полностью** не пересекающийся с доступной историей, отклоняется (`400 RANGE_OUT_OF_BOUNDS`); частично выходящий — принимается и помечается `rangeClamped`;
- агрегаты (`sum`/`average`/`max`/`min`/`observationDays`) считаются по всему выбранному диапазону, независимо от `limit`; `truncated` сигнализирует об обрезке;
- календарь на экране качества строится по календарным дням от последней доступной даты с использованием `coverage.missingDates` (а не по последним 28 наблюдениям).

## 7. Даты

- Все даты — `YYYY-MM-DD` в контексте `Europe/Moscow`; сервер проверяет календарную реальность (round-trip), запрещает `from > to` и выход за доступный диапазон; клиент валидирует произвольный диапазон до запроса.

## 8. Provenance

Статусы отображаются раздельно: `freshness` (`MATCH` / `STALE` / `NOT_CONFIRMED`) и `manifestStatus` (`OK` / `NOT_AVAILABLE` / `CORRUPTED`). `STALE` и `NOT_CONFIRMED` сопровождаются предупреждением; `CORRUPTED` показывается как конфликтный статус, данные не выдаются за корректные. Внутренние пути и служебные детали в UI не выводятся.

## 9. Безопасность

Bind `127.0.0.1`, Host/Origin guard, `no-store`/`nosniff`/`no-referrer`, только GET, отсутствие внешнего CORS, `escapeHtml` + `TrustedHtml`, allowlist SVG-классов, ошибки с `eventId` без stack trace. PII не выводится: `dimension_1`/`dimension_2` в API отсутствуют, данные slice 20404 с маской не используются.
